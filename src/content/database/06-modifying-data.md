Reading data can't hurt anyone. Writing it can. An `UPDATE` without a `WHERE` has ended more
careers' good weeks than any other line of SQL. This lesson covers the **DML** (data
manipulation language) statements — `INSERT`, `UPDATE`, `DELETE` — plus two Postgres features
your backend will use all the time: **RETURNING** and **ON CONFLICT** (upsert). And it builds the
habits that keep you safe when you run them against real data.

:::tip title="The challenges here grade the database state"
For each challenge, a hidden **check query** runs after your SQL and compares the resulting table
contents with the expected state. Every run starts from a fresh database, so a bad `DELETE` only
costs you a retry.
:::

## INSERT

```sql
INSERT INTO categories (id, name) VALUES (6, 'Cables');
```

Always **list the columns**. `INSERT INTO categories VALUES (6, 'Cables')` relies on the
column order of the table and breaks the day someone adds or reorders a column — worse, if two
columns have compatible types it can silently put values in the wrong column.

What about the columns you leave out?

- They get their **`DEFAULT`** value if the table defines one (e.g. `stock integer DEFAULT 0`),
  otherwise **NULL**.
- A `NOT NULL` column with no default **must** be provided — Postgres rejects the row with
  *null value in column "…" of relation "…" violates not-null constraint*.
- Inside `VALUES` you can also write the keyword `DEFAULT` explicitly:
  `INSERT INTO products (id, name, category_id, price, stock) VALUES (13, 'Webcam', 5, 69.00, DEFAULT)`.

:::info title="Where do ids come from?"
The practice datasets use plain `integer PRIMARY KEY` columns with fixed ids (`6`, `11`, …), and
the challenges in this lesson ask you to insert explicit ids too (customer `11`, categories `6`
and `7`, ledger rows `15` and `16`). That's a fixture convention, not advice: fixed ids make the expected database state
predictable, so the grader can compare it row by row. In a real table the id is generated by the
database — an **identity column** (the **Tables, Types & Constraints** lesson) — and you simply leave it out of the column list:
`INSERT INTO notes (body) VALUES ('hi') RETURNING id;`. If a real table must also accept
imported ids, declare it `GENERATED BY DEFAULT AS IDENTITY` (the **Tables, Types & Constraints** lesson shows the sequence pitfall
that comes with it).
:::

Several rows in one statement:

```sql
INSERT INTO categories (id, name) VALUES
  (6, 'Cables'),
  (7, 'Headsets');
```

This is faster than a loop of single inserts (one round trip, one statement to plan) and it is
**atomic**: every SQL statement either succeeds completely or has no effect, so if row 2 breaks
a constraint, row 1 is not inserted either.

:::warn title="Common mistake: double quotes"
In SQL, **single quotes** are text values and **double quotes** are identifiers (table/column
names). `VALUES (6, "Cables")` fails with *column "Cables" does not exist* — Postgres thinks
you're referring to a column. Use `'Cables'`.
:::

### INSERT … SELECT

Instead of `VALUES`, you can insert the result of a query. This is how you copy, archive or
transform data inside the database without a round trip through your app — the rows never
leave the server, so a million-row copy takes seconds instead of minutes. The `SELECT` must
produce columns in the **same order and with compatible types** as the column list (names don't
matter, positions do):

```sql
INSERT INTO orders_archive (id, customer_id, status, ordered_at)
SELECT id, customer_id, status, ordered_at
FROM orders
WHERE ordered_at < '2025-01-01';
```

:::sql id=db-06-sql3 db=shop xp=30
title: Archive cancelled orders
An empty table `orders_archive` (same columns as `orders`) has been created. Copy **all
cancelled orders** into it with a single `INSERT … SELECT`.

hint: `INSERT INTO orders_archive (id, customer_id, status, ordered_at) SELECT … FROM orders WHERE …`

```sql setup
CREATE TABLE orders_archive (
  id integer PRIMARY KEY,
  customer_id integer NOT NULL,
  status text NOT NULL,
  ordered_at timestamp NOT NULL
);
```

```sql starter
INSERT INTO orders_archive (id, customer_id, status, ordered_at)
SELECT id, customer_id, status, ordered_at FROM orders;
```

```sql solution
INSERT INTO orders_archive (id, customer_id, status, ordered_at)
SELECT id, customer_id, status, ordered_at FROM orders WHERE status = 'cancelled';
```

```sql check
SELECT id, customer_id, status, ordered_at FROM orders_archive ORDER BY id;
```
:::

## UPDATE

```sql
UPDATE products
SET price = price * 1.05, stock = stock + 10
WHERE category_id = 2;
```

`SET` can change several columns and can use the row's current values (`price * 1.05`). All
expressions on the right-hand side see the row **as it was before the update**, so
`SET a = b, b = a` really swaps two columns. The `WHERE` decides **which rows** change — leave
it out and **every row** changes. Postgres reports how many rows matched (`UPDATE 4`); that
number is your first sanity check.

:::warn title="Never run UPDATE or DELETE without WHERE in production"
Seriously. And the safe habit is mechanical, not a matter of being careful:

1. Write the `SELECT` first: `SELECT * FROM products WHERE category_id = 2;` — look at the rows.
2. Turn it into the `UPDATE` with the **same** `WHERE`.
3. Run it inside a transaction (`BEGIN; … ;`), check the reported row count, then `COMMIT` — or
   `ROLLBACK` if the number surprises you.
:::

:::sql id=db-06-sql4 db=shop xp=30
title: Price increase
All **Accessories** (category `5`) get 10% more expensive. Update their price to
`price * 1.10`, **rounded to 2 decimals**. Other products must not change.

hint: `UPDATE products SET price = round(price * 1.10, 2) WHERE …`

```sql starter
UPDATE products SET price = round(price * 1.10, 2);
```

```sql solution
UPDATE products SET price = round(price * 1.10, 2) WHERE category_id = 5;
```

```sql check
SELECT id, price FROM products ORDER BY id;
```
:::

### UPDATE … FROM: conditions from another table

Often the rows to update are defined by *another* table. Postgres's `UPDATE … FROM` joins it in;
the join condition goes in `WHERE`:

```sql
-- deactivate every product in the 'Books' category
UPDATE products p
SET active = false
FROM categories c
WHERE c.id = p.category_id
  AND c.name = 'Books';
```

Read it as: "join `products` with `categories`, keep the pairs that pass the `WHERE`, and update
the `products` side of each pair". Don't repeat the target table in `FROM` — `UPDATE products
… FROM products, categories` joins the table with *itself* and usually updates every row.

The standard-SQL alternative is a subquery: `WHERE category_id IN (SELECT id FROM categories
WHERE name = 'Books')` (or `WHERE EXISTS (…)`). Both are fine; `UPDATE … FROM` is handy when you
also need to **copy a value** from the other table into `SET`.

:::warn title="UPDATE … FROM with several matches"
If one target row joins to **several** rows in `FROM`, Postgres updates it only once, using an
**unpredictable** one of the matches — no error. When you copy values from another table, make
sure the join yields at most one row per target row (join on a unique key, or aggregate first).
:::

:::sql id=db-06-sql5 db=shop xp=40
title: Cancel stale German orders
Due to a payment-provider outage in Germany, every **pending** order of a customer whose
`country` is `Germany` must be set to `cancelled`. Pending orders of other countries stay
pending.

hint: `UPDATE orders o SET status = 'cancelled' FROM customers c WHERE c.id = o.customer_id AND …`

```sql starter
UPDATE orders SET status = 'cancelled' WHERE status = 'pending';
```

```sql solution
UPDATE orders o
SET status = 'cancelled'
FROM customers c
WHERE c.id = o.customer_id
  AND c.country = 'Germany'
  AND o.status = 'pending';
```

```sql check
SELECT id, status FROM orders ORDER BY id;
```
:::

## DELETE

```sql
DELETE FROM order_items WHERE order_id = 5;
```

Same rule: no `WHERE` = all rows. Foreign keys protect you from orphans (child rows pointing to
a parent that no longer exists): deleting an order that still has `order_items` fails with
*update or delete on table "orders" violates foreign key constraint … on table "order_items"* —
unless the FK was declared `ON DELETE CASCADE` (the **Tables, Types & Constraints** lesson). Without cascade, delete **children
first, then the parent**.

Like `UPDATE … FROM`, Postgres has `DELETE … USING` to filter by another table:

```sql
-- delete the order lines of all cancelled orders
DELETE FROM order_items oi
USING orders o
WHERE o.id = oi.order_id
  AND o.status = 'cancelled';
```

**`TRUNCATE`** is the bulldozer: `TRUNCATE order_items;` empties the whole table at once instead
of deleting row by row, so it's near-instant even on huge tables. Things to know:

- It has no `WHERE` — it's always *everything*.
- It refuses to truncate a table that other tables reference with a foreign key, unless you
  truncate them together or add `CASCADE` (which empties the referencing tables too!).
- `RESTART IDENTITY` also resets identity counters, so the next id starts at 1 again.
- In Postgres it *is* transactional (`BEGIN; TRUNCATE …; ROLLBACK;` brings the rows back), but
  outside a transaction it's gone. Great for test databases, terrifying anywhere else.

:::sql id=db-06-sql6 db=shop xp=40
title: Purge cancelled orders
Delete **all cancelled orders** together with their order lines. The foreign key from
`order_items` to `orders` has no cascade, so the starter fails — fix the order of operations.

hint: Delete the `order_items` of cancelled orders first: `WHERE order_id IN (SELECT id FROM orders WHERE status = 'cancelled')`.
hint: Then delete the orders themselves.

```sql starter
DELETE FROM orders WHERE status = 'cancelled';
```

```sql solution
DELETE FROM order_items
WHERE order_id IN (SELECT id FROM orders WHERE status = 'cancelled');
DELETE FROM orders WHERE status = 'cancelled';
```

```sql check
SELECT 'orders' AS t, string_agg(id::text, ',' ORDER BY id) FROM orders
UNION ALL
SELECT 'items', count(*)::text FROM order_items;
```
:::

## RETURNING: get the changed rows back

Postgres can return rows from `INSERT`, `UPDATE` and `DELETE` — no second query needed:

```sql
INSERT INTO categories (id, name) VALUES (6, 'Cables') RETURNING id, name;

UPDATE products SET stock = stock - 1 WHERE id = 3 RETURNING id, stock;

DELETE FROM orders WHERE status = 'cancelled' RETURNING id;
```

Why does this matter? Without `RETURNING`, "insert, then find out the new id" needs a second
query — and "decrement stock, then read it" can race with another request that changes the row
in between. `RETURNING` gives you the values **from the same statement**, so they're guaranteed
to belong to *your* change. Your backend uses this constantly: insert a row and get the generated
`id` back (`INSERT … RETURNING id`), or decrement stock and immediately know the new value. EF
Core's Npgsql provider uses `RETURNING` under the hood to fetch generated keys after `SaveChanges`.

### Before and after: `RETURNING old` / `new` (Postgres 18)

For `UPDATE`, plain `RETURNING price` gives the **new** value. Since Postgres 18 you can ask for
both sides with the `old` and `new` row aliases — perfect for audit logs ("price changed from X
to Y") without reading the row first:

```sql
UPDATE products SET price = 26.90 WHERE id = 10
RETURNING id, old.price AS old_price, new.price AS new_price;
-- id | old_price | new_price
-- 10 |     24.90 |     26.90
```

For `INSERT`, `old` is NULL (there was no old row); for `DELETE`, `new` is NULL. In an
`ON CONFLICT DO UPDATE`, `old` is non-NULL exactly when the row already existed — an easy way to
tell "inserted" from "updated".

## Upserts with ON CONFLICT

"Insert this row — or, if it already exists, update it" is everywhere: counters, settings,
syncing data from another system, idempotent API endpoints. Doing it as "SELECT, then INSERT or
UPDATE" in the app has a **race condition**: two requests both see "not there" and both insert.

Postgres does it atomically with `INSERT … ON CONFLICT`:

```sql
-- add 1 view, or create the row with 1 view
INSERT INTO page_views (path, views) VALUES ('/pricing', 1)
ON CONFLICT (path) DO UPDATE SET views = page_views.views + EXCLUDED.views;
```

How it works: Postgres tries the insert; if the new row would violate the unique index you
named, it does the `DO …` part **instead**, on the existing row, while holding a lock on it. A
concurrent request can't sneak in between, because the unique index itself is the referee.

- `ON CONFLICT (path)` is the **conflict target**: the column(s) of a **unique constraint** (or
  primary key) that define "already exists". It must exist — you can't upsert on a column
  without a unique index. (You can also name it: `ON CONFLICT ON CONSTRAINT page_views_pkey`.)
- `EXCLUDED` is the row you *tried* to insert. `page_views.views` (the table name) is the
  existing row.
- `DO NOTHING` simply skips conflicting rows — perfect for "insert if not already there".
- `DO UPDATE SET … WHERE …` only updates when the condition holds, e.g.
  `WHERE page_views.updated_at < EXCLUDED.updated_at` ("only overwrite with newer data").

Three errors you *will* hit:

| Error | Cause | Fix |
|---|---|---|
| *column reference "views" is ambiguous* | `SET views = views + 1` — both the existing row and `EXCLUDED` have a `views` | Qualify: `page_views.views + 1` |
| *ON CONFLICT DO UPDATE command cannot affect row a second time* | The same key appears **twice in one statement** (e.g. a batch with two `/docs` rows) | De-duplicate the batch first |
| *there is no unique or exclusion constraint matching the ON CONFLICT specification* | No unique index on the conflict target columns | Add a `UNIQUE` constraint |

Also note the conflict target only covers **that** constraint: `ON CONFLICT (email) DO NOTHING`
still raises an error if the same row clashes on the primary key. (Plain `ON CONFLICT DO NOTHING`
without a target skips conflicts on *any* unique constraint.)

:::sql id=db-06-sql9 db=empty xp=40

Table `page_views(path PRIMARY KEY, views)` already has `/` (10 views) and `/pricing` (3 views).
In **one** `INSERT` statement, record **one view** each for `/pricing` and `/docs`: existing paths
get `views + 1`, new paths start at `1`.

hint: `INSERT … VALUES ('/pricing', 1), ('/docs', 1) ON CONFLICT (path) DO UPDATE SET …`
hint: `SET views = page_views.views + EXCLUDED.views`

```sql setup

```

```sql starter

ON CONFLICT (path) DO NOTHING;
```

```sql solution

ON CONFLICT (path) DO UPDATE SET views = page_views.views + EXCLUDED.views;
```

```sql check
SELECT path, views FROM page_views ORDER BY path;
```
:::

:::info title="What about MERGE?"
Postgres 15+ also supports the SQL-standard `MERGE` (and Postgres 17 added `RETURNING` to it),
which can insert, update **and delete** in one statement based on a join with a source table —
useful for batch syncs. For a single-row "insert or update" under concurrency, prefer
`ON CONFLICT`: `MERGE` doesn't use the unique index as a referee, so two concurrent `MERGE`s can
still both try to insert and one fails with a unique-violation error.
:::

## Transactions: all or nothing

A **transaction** groups statements so they succeed or fail **together**. Moving credits from
one user to another is two writes; if the second one fails, the first must not stay.

```sql
BEGIN;
INSERT INTO credit_ledger (id, user_id, delta, reason, created_at)
VALUES (15, 1, -50, 'gift to Lena', '2025-08-01 12:00+00');
INSERT INTO credit_ledger (id, user_id, delta, reason, created_at)
VALUES (16, 5,  50, 'gift from Mara', '2025-08-01 12:00+00');
COMMIT;      -- or ROLLBACK; to undo everything since BEGIN
```

(The explicit ids `15` and `16` are only there so the challenge below can check an exact state; a
real ledger would have an identity `id` and leave it out of the `INSERT`.)

What you need to know about how it behaves:

- **Autocommit.** Outside `BEGIN`, every statement is its own transaction and is committed
  immediately (that's the default in `psql`, pgAdmin and drivers). There is no undo button.
- **Isolation.** Inside a transaction, other sessions don't see your changes until `COMMIT`
  (the Transactions, Isolation & Locking lesson covers isolation levels and locks).
- **Errors abort the whole transaction.** If any statement fails, Postgres marks the transaction
  as *aborted*: every following statement fails with *current transaction is aborted, commands
  ignored until end of transaction block*, and even `COMMIT` then performs a `ROLLBACK`. Nothing
  from that transaction is written.

In backend code you do the same with Npgsql, or let EF Core's `SaveChanges` wrap all pending
changes in one transaction for you:

```csharp
await using var tx = await conn.BeginTransactionAsync();
// … execute both INSERT commands with this connection …
await tx.CommitAsync();   // disposing without Commit rolls back
```

:::

:::quiz id=db-06-q1 xp=15
You run `UPDATE products SET price = 0;` in `psql` (no `BEGIN`). What happens?
- [ ] Postgres asks for confirmation
- [ ] Only the first row changes
- [x] Every product's price becomes 0, committed immediately
- [ ] It fails because there is no WHERE
> Without WHERE, every row matches, and outside an explicit transaction psql auto-commits. A
> missing WHERE is perfectly valid SQL, so Postgres neither refuses nor asks — that safety net
> doesn't exist (some GUI tools add a warning, the database never does). Your only way back is a
> backup or point-in-time recovery. Write the SELECT first, use BEGIN, check the count.
:::

:::quiz id=db-06-q2 xp=15
`INSERT … ON CONFLICT (email) DO UPDATE …` fails with *there is no unique or exclusion
constraint matching the ON CONFLICT specification*. Why?
- [ ] `DO UPDATE` needs a `WHERE` clause
- [x] The `email` column has no UNIQUE constraint / unique index
- [ ] You can only upsert on the primary key
- [ ] `EXCLUDED` must be declared first
> ON CONFLICT relies on a unique index to detect "already exists" — that's exactly what the error
> message says is missing. It's tempting to think only the primary key works, but **any** unique
> constraint or unique index works (`ALTER TABLE … ADD UNIQUE (email)` fixes it). A `WHERE` on
> `DO UPDATE` is optional, and `EXCLUDED` is built in, never declared.
:::

:::quiz id=db-06-q3 xp=10
Why use `INSERT … ON CONFLICT` instead of "SELECT; if missing then INSERT else UPDATE" in your
API code?
- [ ] It's shorter, nothing else
- [x] It's atomic: two concurrent requests can't both decide "missing" and insert twice
- [ ] It skips constraint checks, so it's faster
> Check-then-act in application code has a race window between the SELECT and the INSERT: two
> requests can both see "missing", and one of them then crashes on the unique constraint (or, with
> no constraint, you get a duplicate). The upsert is a single atomic statement refereed by the
> unique index. It's not "just shorter", and it certainly doesn't skip constraint checks — the
> constraint is what makes it work.
:::

:::quiz id=db-06-q4 xp=15
In `psql` you run:

```sql
BEGIN;
INSERT INTO categories (id, name) VALUES (6, 'Cables');
INSERT INTO categories (id, name) VALUES (1, 'Duplicate');   -- id 1 already exists
INSERT INTO categories (id, name) VALUES (7, 'Headsets');
COMMIT;
```

Which new categories exist afterwards?
- [ ] `6` and `7` — only the failing statement is skipped
- [ ] Only `6` — everything before the error is kept
- [x] None — the error aborts the transaction and `COMMIT` rolls it back
- [ ] `6`, `7` and the duplicate is renamed automatically
> After the duplicate-key error the transaction is *aborted*: the `INSERT` of 7 fails with
> "current transaction is aborted", and `COMMIT` reports `ROLLBACK`. That's the point of a
> transaction — all or nothing. "Keep what worked before the error" is how autocommit mode behaves
> (each statement on its own), not how a transaction behaves.
:::

:::quiz id=db-06-q5 xp=15
Spot the bug. This upsert fails — why?

```sql
INSERT INTO page_views (path, views) VALUES ('/docs', 1)
ON CONFLICT (path) DO UPDATE SET views = views + 1;
```

- [ ] `DO UPDATE` can't use arithmetic
- [x] `views` on the right side is ambiguous: it could mean the existing row or `EXCLUDED`
- [ ] The column list must not include `views`
- [ ] `ON CONFLICT` needs `ON CONSTRAINT` instead of a column list
> Inside `DO UPDATE`, two rows are in scope — the existing one (`page_views`) and the proposed one
> (`EXCLUDED`) — so Postgres raises *column reference "views" is ambiguous*. Write
> `page_views.views + 1` (or `+ EXCLUDED.views`). Arithmetic is fine, and a column list is the
> normal way to give the conflict target. (The left side of `SET` is never ambiguous: it's always
> the target table's column.)
:::

:::quiz id=db-06-q6 xp=15
`customers` has `id` as primary key and a `UNIQUE` constraint on `email`. Customer 3 already
exists. What does this do?

```sql
INSERT INTO customers (id, name, email, country, created_at)
VALUES (3, 'New Person', 'new@example.com', 'USA', '2025-08-01')
ON CONFLICT (email) DO NOTHING;
```

- [ ] Inserts nothing silently, because a conflict happened
- [x] Fails with a duplicate-key error on the primary key
- [ ] Overwrites customer 3 with the new values
- [ ] Inserts a second row with id 3
> The conflict target `(email)` only covers the email constraint — and `new@example.com` doesn't
> clash. The clash is on `id`, which this clause doesn't handle, so the normal unique-violation
> error is raised. To skip *any* conflict, write `ON CONFLICT DO NOTHING` without a target;
> `DO NOTHING` never overwrites, and a primary key never allows two rows with the same id.
:::

:::pro title="Make writes idempotent"
Networks retry. A payment webhook may arrive twice; a user may double-click "Save". Seniors design
writes so that running them twice is harmless: an idempotency key with a unique constraint and
`ON CONFLICT DO NOTHING`, or an upsert that sets absolute values rather than `+ 1`.

That doesn't make `+ 1` wrong — it answers a different question. An increment like
`SET views = page_views.views + 1` is **atomic** (two concurrent requests can't lose an update;
the Transactions, Isolation & Locking lesson relies on exactly this for counters) but **not idempotent** (a retried request counts
twice). When you need both, pair them: insert the event's id into a dedupe table with
`ON CONFLICT DO NOTHING`, and only increment if that insert actually added a row — in one
transaction, or one statement with a CTE (the **Subqueries, CTEs & Recursive Queries** lesson).
:::

:::job title="Production data changes go through review"
On most teams, ad-hoc writes to production are rare and controlled: a reviewed migration or
script, run in a transaction, with the expected row count written in the PR ("updates 312 rows").
Many companies give developers read-only production access by default. Treat any write prompt on
a production database like `rm -rf` on a server.
:::

:::cards id=db-06-cards1 xp=15 title="Modifying data"
Q: Why list columns in INSERT?
A: So the statement doesn't depend on the table's column order and survives new columns.
Q: Copy rows from a query into a table?
A: `INSERT INTO t (cols) SELECT … FROM …`.
Q: Update based on another table?
A: `UPDATE t SET … FROM other o WHERE o.id = t.other_id AND …`.
Q: Deleting a parent with children (no cascade)?
A: Delete the children first, then the parent — or the FK blocks it.
Q: What does RETURNING do?
A: Returns columns of the inserted/updated/deleted rows, e.g. the generated id.
Q: Upsert syntax?
A: `INSERT … ON CONFLICT (unique_col) DO UPDATE SET col = EXCLUDED.col` (or DO NOTHING).
Q: What is EXCLUDED?
A: The row that was proposed for insertion in an ON CONFLICT DO UPDATE.
Q: Safe-update routine?
A: SELECT with the same WHERE first → BEGIN → UPDATE → check row count → COMMIT or ROLLBACK.
Q: TRUNCATE vs DELETE?
A: TRUNCATE empties the whole table instantly (no WHERE, blocked by FKs unless CASCADE); DELETE removes matching rows one by one (with WHERE).
Q: Delete based on another table?
A: `DELETE FROM t USING other o WHERE o.id = t.other_id AND …` (or a subquery in WHERE).
Q: Get the value before and after an UPDATE (Postgres 18)?
A: `RETURNING old.col, new.col`.
Q: "column reference is ambiguous" in an upsert?
A: Qualify the existing row's column with the table name: `SET views = page_views.views + 1`.
Q: What happens after an error inside BEGIN … COMMIT?
A: The transaction is aborted: later statements fail and COMMIT rolls everything back.
:::

## Recap

- `INSERT` with an explicit column list; multi-row `VALUES`; `INSERT … SELECT` to copy data.
- `UPDATE … SET … WHERE`; `UPDATE … FROM` / `DELETE … USING` to use another table (watch for
  multiple matches); `DELETE` children before parents.
- **No WHERE = every row.** SELECT first, wrap in a transaction, check the count.
- `RETURNING` gives back the affected rows (generated ids, new values); Postgres 18 adds
  `old.` / `new.` for before-and-after values.
- `ON CONFLICT (…) DO UPDATE / DO NOTHING` is an atomic upsert; it needs a unique constraint;
  `EXCLUDED` is the proposed row; qualify columns to avoid ambiguity.
- Transactions make several writes all-or-nothing: `BEGIN … COMMIT / ROLLBACK`; one error aborts
  the whole transaction.
