Writing correct SQL is half the job. The other half is keeping a database **alive in production**:
changing its schema while thousands of requests per second hit it, making sure one tenant can never
read another tenant's data, being able to restore *last Tuesday at 14:29* after someone runs a bad
`DELETE`, and not running out of connections when you scale the API to 20 pods.

This lesson is the operational toolkit a senior full-stack developer is expected to know. The
challenges run on the **studio** dataset (a multi-tenant branching-video SaaS) and on small custom
tables. Two neighboring lessons cover the rest: **Postgres From Your Code** (parameters,
transactions, retries and integration tests from C# and Node) and **Multi-Tenancy, Partitioning &
Temporal Data** (tenancy models, history tables and declarative partitioning).

:::info title="What the browser can and can't show"
The in-browser Postgres runs your SQL as a **single transaction on a single connection**. Real lock
contention, `CREATE INDEX CONCURRENTLY` (which refuses to run inside a transaction), `VACUUM`
statistics and backups can't be demonstrated live here — they're explained with timelines and
quizzes. Everything you write in the challenges is the same SQL you'd ship.
:::

## Migrations: the schema is code

Production schemas are never changed by hand in pgAdmin. Every change is a **migration** — a
versioned, reviewed, repeatable script — applied in order by a tool, and recorded in a history table
so each one runs exactly once per database.

| Tool | Migration files | History table | Notes |
|---|---|---|---|
| **EF Core** | C# classes generated by `dotnet ef migrations add AddSlug` | `__EFMigrationsHistory` | generate SQL with `dotnet ef migrations script --idempotent`, or build a self-contained `dotnet ef migrations bundle` |
| **Flyway** | `V7__add_project_slug.sql`, `R__views.sql` (repeatable) | `flyway_schema_history` | plain SQL, checksums detect edited files |
| Liquibase, Sqitch, golang-migrate, Prisma, Knex… | similar ideas | | |

The workflow on a real team:

1. Change the model / write the SQL **on a branch**, generate the migration, commit it with the code.
2. CI applies all migrations to a fresh Postgres (Testcontainers) and runs the integration tests.
3. A reviewer reads the **generated SQL**, not just the C# — looking for locks and rewrites (below).
4. The deploy pipeline runs migrations as a **separate step** (a Kubernetes `Job`, an init step,
   or the bundle executable) *before* the new app version rolls out.

:::warn title="Rules that prevent outages"
- **Never edit a migration that has run anywhere shared.** Flyway's checksum will fail; EF Core will
  silently skip it on databases that already applied it. Write a new migration instead.
- **Don't call `Database.Migrate()` at startup of every replica.** EF Core 9+ takes a database lock
  so two pods can't apply the same migration at once, but the other nine pods still block their
  startup (and fail readiness/liveness probes) while one runs a long migration, a failed migration
  becomes a crash-looping deployment, and every pod needs DDL rights. Run it once, as its own step,
  with its own (more privileged) database role.
- **Every migration must be compatible with the app version that's still running.** During a rolling
  deploy, old and new pods run side by side against the *same* schema.
:::

## Zero-downtime schema changes

That last rule is the heart of zero-downtime deploys. You can't rename a column in one step: the
old pods still `SELECT display_name` the moment after you rename it. Instead you use
**expand / contract** (a.k.a. parallel change):

| Phase | Schema | App |
|---|---|---|
| **1. Expand** | add the new thing (nullable column, new table, new index), keep the old | old version still running, unaware |
| **2. Migrate** | backfill data in batches; keep old & new in sync (dual write from app or trigger) | deploy a version that writes both, reads new |
| **3. Contract** | once no running code uses the old thing: drop it, add the final constraints | deploy the version that only knows the new thing |

Each phase is a separate deploy. It feels slow; it's what lets you deploy on a Tuesday afternoon.

### Locks are the real danger

Every statement takes a **table-level lock** before touching a table: a plain `SELECT` takes the
weakest one (`ACCESS SHARE`), `INSERT`/`UPDATE`/`DELETE` take `ROW EXCLUSIVE`, and two locks only
block each other if their modes *conflict*. Most `ALTER TABLE` forms take the strongest mode,
**`ACCESS EXCLUSIVE`** — it conflicts with *everything*, including plain `SELECT`. Usually held for
milliseconds, it's harmless. The disaster is the **lock queue**: lock requests are granted in
arrival order, so a request that is *waiting* for `ACCESS EXCLUSIVE` also makes every later
request wait behind it, even ones that would be compatible with the current holder.

| Time | Session A (report) | Session B (migration) | Sessions C, D, E… (API) |
|---|---|---|---|
| 10:00:00 | `BEGIN; SELECT … FROM projects` (long, 2 min) | | |
| 10:00:01 | still running — holds `ACCESS SHARE` | `ALTER TABLE projects ADD COLUMN slug text;` → **waits** for A | |
| 10:00:02 | | waiting, queued for `ACCESS EXCLUSIVE` | `SELECT * FROM projects WHERE id = 1` → **waits behind B** |
| 10:00:30 | | still waiting | hundreds of API requests queued; pool exhausted; **site down** |
| 10:02:00 | `COMMIT` | gets lock, finishes in 2 ms | everything resumes |

A "metadata-only" change took the site down for two minutes because it **waited** for its lock while
blocking everyone queued behind it. The fix is to give up quickly and retry:

```sql
SET lock_timeout = '3s';        -- fail fast instead of queueing the world behind us
SET statement_timeout = '15min'; -- and don't let a migration run forever
ALTER TABLE projects ADD COLUMN slug text;   -- if it times out, the tool retries later
```

What each common operation costs:

| Operation | Lock | Rewrites / scans table? | Safe pattern |
|---|---|---|---|
| `ADD COLUMN` (nullable, or non-volatile default such as `'free'` or `now()` — PG 11+) | ACCESS EXCLUSIVE, brief | no | fine with `lock_timeout` |
| `ADD COLUMN … DEFAULT gen_random_uuid()` / `clock_timestamp()` (volatile default) | ACCESS EXCLUSIVE | **rewrite** | add nullable, backfill in batches |
| `ALTER COLUMN … TYPE` (most changes) | ACCESS EXCLUSIVE | **rewrite** | new column + backfill + switch |
| `SET NOT NULL` | ACCESS EXCLUSIVE | **full scan** | validated `CHECK (col IS NOT NULL)` first, or PG 18 `NOT NULL … NOT VALID` + `VALIDATE` |
| `ADD CONSTRAINT … CHECK` | ACCESS EXCLUSIVE | **full scan** | `NOT VALID`, then `VALIDATE CONSTRAINT` (weaker lock) |
| `ADD CONSTRAINT … FOREIGN KEY` | SHARE ROW EXCLUSIVE on both tables — blocks writes | **full scan** | `NOT VALID`, then `VALIDATE CONSTRAINT` |
| `CREATE INDEX` | SHARE — **blocks writes** | builds index | `CREATE INDEX CONCURRENTLY` |
| `DROP COLUMN` | ACCESS EXCLUSIVE, brief | no (marks dropped) | only after no code reads it |
| `RENAME COLUMN` | ACCESS EXCLUSIVE, brief | no | breaks running code → expand/contract instead |

Why is `DEFAULT now()` cheap but `DEFAULT gen_random_uuid()` a rewrite? Since PG 11, a
**non-volatile** default is evaluated *once* during the `ALTER` and stored in the catalog as the
value for all existing rows — nothing is written to the table. `now()` is *stable* (the same
value for the whole transaction), so every old row gets the same timestamp. A **volatile**
function must produce a different value per row, so Postgres has to rewrite every row under
`ACCESS EXCLUSIVE`.

:::quiz id=db-16-q5 xp=15
On a 300-million-row `clips` table (PostgreSQL 18), which migration holds an `ACCESS EXCLUSIVE`
lock for **as long as it takes to rewrite the whole table**?

- [ ] `ALTER TABLE clips ADD COLUMN visibility text NOT NULL DEFAULT 'private';`
- [ ] `ALTER TABLE clips ADD COLUMN imported_at timestamptz DEFAULT now();`
- [x] `ALTER TABLE clips ADD COLUMN public_id uuid NOT NULL DEFAULT gen_random_uuid();`
- [ ] `ALTER TABLE clips DROP COLUMN legacy_notes;`
> `gen_random_uuid()` is **volatile**: every existing row needs its own value, so Postgres rewrites
> the table while blocking reads and writes. A constant default and `now()` (stable — one value for
> the whole transaction) are stored once in the catalog, so the `ADD COLUMN` is metadata-only even with
> `NOT NULL`. `DROP COLUMN` only marks the column as dropped. The safe path for the UUID: add it
> nullable, then `ALTER COLUMN public_id SET DEFAULT gen_random_uuid()` (metadata-only, it applies
> only to new rows), backfill the old rows in batches, then add `NOT NULL` through a validated
> constraint.
:::

### NOT VALID + VALIDATE

Adding a `CHECK` or `FOREIGN KEY` normally scans the whole table to prove every existing row
satisfies it — while holding a lock that blocks writes (and, for `CHECK`, reads too). Split the
"enforce from now on" part from the "prove the old rows" part:

```sql
-- instant: enforced for all NEW writes from now on; existing rows not checked yet
ALTER TABLE render_jobs
  ADD CONSTRAINT render_jobs_attempts_nonneg CHECK (attempts >= 0) NOT VALID;

-- later (maybe after fixing old rows): scans the table under SHARE UPDATE EXCLUSIVE,
-- which allows reads AND writes to continue
ALTER TABLE render_jobs VALIDATE CONSTRAINT render_jobs_attempts_nonneg;
```

The `ADD … NOT VALID` still needs a brief `ACCESS EXCLUSIVE` lock (so keep `lock_timeout` on), but
it doesn't scan, so it's held for milliseconds. If `VALIDATE` finds a bad row it fails with the
usual violation error and the constraint simply stays `NOT VALID` — fix the data and run it again.

The same trick makes `SET NOT NULL` cheap: once a **validated** `CHECK (slug IS NOT NULL)` exists,
Postgres skips the full-table scan for `SET NOT NULL`. PostgreSQL 18 goes one step further and allows
`NOT NULL` constraints themselves to be `NOT VALID`:
`ALTER TABLE projects ADD CONSTRAINT projects_slug_nn NOT NULL slug NOT VALID;`

### CREATE INDEX CONCURRENTLY

```sql
CREATE INDEX CONCURRENTLY projects_owner_idx ON projects (owner_id);
```

It builds the index without blocking writes (it waits for existing transactions and scans twice),
at the cost of time. Caveats: it **can't run inside a transaction block** (in EF Core with Npgsql,
configure the index with `.IsCreatedConcurrently()` or write
`migrationBuilder.Sql("CREATE INDEX CONCURRENTLY …", suppressTransaction: true)`; in Flyway, a
non-transactional migration), and if it fails it leaves an `INVALID` index you must drop and retry.
`DROP INDEX CONCURRENTLY` and `REINDEX CONCURRENTLY` exist too.

:::sql id=db-16-sql1 db=studio ordered=true xp=70
title: Add a required, unique slug — safely
The public share page needs `projects.slug` (e.g. `the-heist`). The naive migration in the starter
fails on a table that already has rows. Write the safe sequence:

1. add `slug text` as a **nullable** column,
2. backfill it: lower-case title, every run of non-alphanumeric characters replaced by `-`,
   leading/trailing `-` trimmed,
3. make it `NOT NULL` via a `NOT VALID` constraint that you then `VALIDATE`
   (a `CHECK (slug IS NOT NULL)` followed by `SET NOT NULL`, or PG 18's `NOT NULL … NOT VALID`),
4. add a **unique** index on `slug`.

We check `id, slug`, the column's nullability, whether every constraint on `projects` is validated,
and whether a unique index on `(slug)` exists.

hint: `btrim(lower(regexp_replace(title, '[^a-zA-Z0-9]+', '-', 'g')), '-')`
hint: `ALTER TABLE projects ADD CONSTRAINT projects_slug_nn NOT NULL slug NOT VALID;` then `ALTER TABLE projects VALIDATE CONSTRAINT projects_slug_nn;`
hint: In production the index would be `CREATE UNIQUE INDEX CONCURRENTLY` in its own migration — here a plain `CREATE UNIQUE INDEX` is fine.

```sql starter

```

```sql solution

-- 2. backfill (in production: in batches, see next challenges)

```

### Backfilling in batches

`UPDATE events SET user_id = (payload->>'uid')::int;` on 200 million rows is one giant transaction,
with all the problems from "Big deletes and updates: do them in chunks" in **Performance Tuning**:
long row locks, a WAL storm that makes replicas lag, 200 million dead row versions, and a rollback
of everything if it fails after an hour. In a migration it is the **migrate** step of expand /
contract, so use the same chunking loop:

```sql
-- run repeatedly (from a script, a background job, or a PROCEDURE with COMMIT) until 0 rows
UPDATE events
SET user_id = (payload ->> 'uid')::int
WHERE id IN (
  SELECT id FROM events
  WHERE user_id IS NULL
  ORDER BY id
  LIMIT 5000
);
```

Here the "rows that still need work" filter is `WHERE user_id IS NULL`, which makes the backfill
resumable. Run it from the migration tool's data step or a background job, not from inside the
schema migration's transaction, so each batch really commits.

:::sql id=db-16-sql4 db=empty xp=50
title: One batch at a time
`events` has 1,000 rows whose new `user_id` column must be backfilled from `payload ->> 'uid'`.
Write the **batch** statement — it backfills the **250 lowest-id rows that still need it** — and
run it **twice** (two batches, as two statements). Don't touch rows outside those batches.

We check how many rows are backfilled, the lowest id still waiting, and whether every backfilled
value is correct.

hint: `UPDATE events SET user_id = (payload ->> 'uid')::int WHERE id IN (SELECT id FROM events WHERE user_id IS NULL ORDER BY id LIMIT 250);`
hint: Paste the same statement twice — the `IS NULL` filter makes the second run pick up the next 250.

```sql setup

```

### Renaming without downtime: dual writes

To rename `users.display_name` to `full_name`, old pods (writing `display_name`) and new pods
(writing `full_name`) run at the same time. During the transition, **both columns must stay in
sync**. The app can do it, but a trigger catches *every* writer — including the admin script nobody
remembered.

:::sql id=db-16-sql5 db=studio ordered=true xp=80
title: Expand phase of a column rename
Write the **expand** migration for renaming `users.display_name` → `full_name`:

1. add a nullable `full_name text`,
2. add a `BEFORE INSERT OR UPDATE` row trigger that keeps both columns in sync:
   - on **INSERT**, whichever of the two is missing is copied from the other,
   - on **UPDATE**, if `display_name` changed, copy it to `full_name`; else if `full_name`
     changed, copy it to `display_name`,
3. backfill `full_name` from `display_name` for the existing rows.

Why the trigger **before** the backfill? On a live system, old pods keep updating `display_name`
while the backfill runs. If the trigger doesn't exist yet, a rename that lands after the backfill
copied that row is never mirrored into `full_name`. Trigger first means every write from then on is
synced, and the backfill only has to handle the past. (The grader only checks the final data, but
this is the order to ship.)

We then simulate old code (writes `display_name` only) and new code (writes `full_name` only) and
check `id, display_name, full_name` for every user.

hint: `IF TG_OP = 'INSERT' THEN NEW.full_name := coalesce(NEW.full_name, NEW.display_name); …`
hint: `ELSIF NEW.display_name IS DISTINCT FROM OLD.display_name THEN NEW.full_name := NEW.display_name;`
hint: `display_name` is `NOT NULL`, but NOT NULL is checked **after** BEFORE triggers run — so the trigger can fill it in.

```sql starter
ALTER TABLE users ADD COLUMN full_name text;
UPDATE users SET full_name = display_name;
```

```sql solution
ALTER TABLE users ADD COLUMN full_name text;

CREATE FUNCTION users_sync_name() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF TG_OP = 'INSERT' THEN
    NEW.full_name    := coalesce(NEW.full_name, NEW.display_name);
    NEW.display_name := coalesce(NEW.display_name, NEW.full_name);
  ELSIF NEW.display_name IS DISTINCT FROM OLD.display_name THEN
    NEW.full_name := NEW.display_name;
  ELSIF NEW.full_name IS DISTINCT FROM OLD.full_name THEN
    NEW.display_name := NEW.full_name;
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER users_sync_name
BEFORE INSERT OR UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION users_sync_name();

-- backfill the past (in production: in batches)
UPDATE users SET full_name = display_name WHERE full_name IS NULL;
```

The **contract** phase, weeks later, once every pod runs the new version: drop the trigger, make
`full_name` `NOT NULL` (NOT VALID + VALIDATE), and `DROP COLUMN display_name`.

:::quiz id=db-16-q1 xp=15
A migration runs `ALTER TABLE projects ADD COLUMN slug text;` — a metadata-only change. Yet the API
timed out for 90 seconds. What's the most likely cause, and the fix?
- [ ] Adding a column rewrites the table; use a smaller table
- [x] The ALTER waited for its ACCESS EXCLUSIVE lock behind a long-running transaction, and every query queued behind it. Set `lock_timeout` and retry.
- [ ] Postgres must rebuild every index; use `CREATE INDEX CONCURRENTLY`
- [ ] Autovacuum blocked the ALTER; disable autovacuum during deploys
> A nullable `ADD COLUMN` doesn't rewrite anything and builds no index, so the "rewrite" and
> "rebuild indexes" answers are wrong; a regular autovacuum cancels itself when DDL needs a
> conflicting lock (only anti-wraparound vacuums don't), and disabling it causes bloat.
> The operation itself takes milliseconds, but a waiting ACCESS EXCLUSIVE request blocks every later
> lock request on the table, even plain SELECTs. A short `lock_timeout` makes the migration give up
> (and retry) instead of stalling the whole site. Also hunt down the long transaction.
:::

## Roles and least privilege

In Postgres, users and groups are both **roles**. A role can `LOGIN` (a user) or not (a group you
grant to others). The goal is **least privilege**: every piece of software gets exactly the rights it
needs, so a SQL injection or leaked password does limited damage.

A typical production setup:

| Role | Can | Used by |
|---|---|---|
| `studio_owner` (NOLOGIN) | owns all tables; `CREATE`, `ALTER`, `DROP` | nothing directly — migrations `SET ROLE` to it |
| `studio_migrator` (LOGIN, member of owner) | run DDL | the CI/CD migration step |
| `studio_app` (LOGIN) | `SELECT/INSERT/UPDATE/DELETE` on app tables — **no DDL** | the API pods |
| `studio_reporting` (LOGIN) | `SELECT` on non-sensitive tables/views | BI tools, analysts |
| `postgres` (superuser) | everything, bypasses RLS | humans in emergencies only |

```sql
CREATE ROLE studio_app LOGIN PASSWORD '…';         -- in practice from a secret manager
GRANT USAGE ON SCHEMA public TO studio_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO studio_app;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO studio_app;  -- for serial / nextval
REVOKE UPDATE, DELETE ON credit_ledger FROM studio_app;       -- the ledger is append-only

-- tables created LATER by the owner get these grants automatically
ALTER DEFAULT PRIVILEGES FOR ROLE studio_owner IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO studio_app;
```

`GRANT … ON ALL TABLES` only affects tables that exist *now* — the classic bug is "the new table from
last sprint returns *permission denied* in production". `ALTER DEFAULT PRIVILEGES` fixes that.
Also `REVOKE CREATE ON SCHEMA public FROM PUBLIC` (the default since PG 15) so the app can't create
objects.

## Row-level security for multi-tenant SaaS

(This section covers RLS itself. Choosing between shared tables, schema-per-tenant and
database-per-tenant, and tenant-safe keys, is in **Multi-Tenancy, Partitioning & Temporal Data**.)

Most SaaS apps are **multi-tenant**: one database, many customers, every table carrying a
`tenant_id` (or `owner_id`, `org_id`). The scariest bug in such a system is a missing
`WHERE tenant_id = @tenant` in one query — and now customer A sees customer B's invoices.

**Row-level security (RLS)** moves that filter into the database. Once enabled on a table, every
query by a non-owner role is automatically filtered by the table's **policies**:

```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON documents
  USING      (tenant_id = nullif(current_setting('app.tenant_id', true), '')::int)   -- rows you can SEE / update / delete
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::int);  -- rows you may WRITE
```

How the app tells Postgres who the tenant is — at the start of **every transaction**:

```sql
BEGIN;
SELECT set_config('app.tenant_id', '42', true);   -- true = local to this transaction (= SET LOCAL)
SELECT * FROM documents;                           -- only tenant 42's rows, no WHERE needed
COMMIT;
```

Details that matter:

- **No policy = no rows.** With RLS enabled and no matching policy, the table looks empty
  (default deny). Missing setting? `current_setting('app.tenant_id', true)` returns NULL, the policy
  is NULL → no rows. Fail closed.
- **The empty-string trap.** Once a custom setting has been set on a connection, "unsetting" it
  (`RESET`, or the end of a `SET LOCAL` transaction) leaves `''`, not NULL — and `''::int` raises
  *invalid input syntax for type integer*. Wrap it: `nullif(current_setting('app.tenant_id', true), '')::int`.
- **Superusers and the table owner bypass RLS.** Your app must connect as a non-owner role (like
  `studio_app`), or you add `ALTER TABLE … FORCE ROW LEVEL SECURITY`. Roles with `BYPASSRLS`
  (for admin jobs) skip it deliberately.
- **`USING` vs `WITH CHECK`**: without `WITH CHECK`, a tenant could `INSERT` a row with someone else's
  `tenant_id`. The violation raises *new row violates row-level security policy*.
- Policies can be per command (`FOR SELECT`, `FOR INSERT` …) and per role (`TO studio_app`), and
  multiple permissive policies are OR-ed.
- **Views run as their owner.** A view created by the table owner reads the table *as the owner*,
  so RLS is silently skipped. Create views with `WITH (security_invoker = true)` (PG 15+) so the
  caller's policies apply.
- **Index `tenant_id`** (usually as the first column of composite indexes) — every query now filters on it.
- Use `SET LOCAL` / `set_config(…, true)`, not plain `SET`, so a pooled connection never carries the
  previous request's tenant into the next one (see pooling below).

:::sql id=db-16-sql7 db=empty xp=70

## Backups: pg_dump vs PITR

First, two terms. **WAL** (write-ahead log) is the journal Postgres writes *before* changing data
files — every change is in it, which is how Postgres recovers after a crash, feeds replicas, and
makes point-in-time restores possible. **RPO** (recovery point objective) is how much data you are
allowed to lose in a disaster, e.g. "at most 5 minutes".

There are two fundamentally different kinds of Postgres backup:

| | **Logical** (`pg_dump` / `pg_restore`) | **Physical** (base backup + WAL archive) |
|---|---|---|
| What | SQL / custom-format dump of schema + data | copy of the data files + every WAL segment since |
| Restore to | the moment the dump started | **any point in time** (PITR) between backups |
| Speed for big DBs | slow dump, very slow restore (rebuild indexes) | fast — copy files, replay WAL |
| Granularity | one database, one table, across major versions | whole cluster, same major version |
| Typical RPO | hours (since last dump) | seconds to minutes |
| Use for | migrations between versions/providers, dev copies, table-level recovery | disaster recovery |

Because every change is in the WAL, a copy of the data files (a **base backup**) plus all WAL written
since is enough to rebuild the database at any later moment. Continuous **WAL archiving** ships each 16 MB segment to object storage (S3, Azure Blob, GCS) as
soon as it fills (or after `archive_timeout`). Restore = take the latest base backup before the
incident, replay archived WAL **up to a target time**, stop. "Restore to 14:29, one minute before
someone ran `DELETE FROM projects` without a `WHERE`" is exactly what PITR is for.

With the backup types in mind, the two numbers on-call engineers care about:

- **RPO** (defined above): WAL archiving gets it down to seconds/minutes.
- **RTO** (recovery time objective): how long restoring may take, driven by base backup size + WAL to replay.

### CloudNativePG on Kubernetes

On Kubernetes, the **CloudNativePG** operator runs Postgres clusters (primary + replicas, automatic
failover) and handles backups via the Barman Cloud plugin: base backups and continuous WAL archiving

```yaml
  name: studio-db-restore

  instances: 1
  storage: { size: 50Gi }

    recovery:
      source: origin
      recoveryTarget:
```

:::job title="Backups you haven't restored are hopes, not backups"
Teams that sleep well run **restore drills**: on a schedule (monthly is common), restore the
production backup to a throwaway cluster, run a smoke query (`SELECT count(*) FROM projects`, the
latest `created_at`), measure how long it took (your real RTO) and write it down. Also keep a
`pg_dump` of critical data in a **different** account/region — replicas and PITR don't protect you
from a deleted cloud account or a ransomware'd bucket. Replicas are *not* backups: they replicate
the `DROP TABLE` too.

## Connection pooling

Every Postgres connection is a separate **process** on the server (several MB of RAM, plus
per-connection caches). `max_connections` is typically 100–500. Meanwhile your API runs 20 pods ×
a pool of 50 connections each = 1,000 potential connections, plus workers, plus cron jobs.

Two levels of pooling solve this:

1. **Client-side pools** (Npgsql, `pg.Pool`, HikariCP) reuse connections *within one process*.
   Configure `Maximum Pool Size` deliberately; the sum over all pods must fit the server.
2. **A server-side pooler — PgBouncer** (or the one built into your managed service, or
   CloudNativePG's `Pooler` resource) sits between apps and Postgres and multiplexes thousands of
   client connections onto a few dozen real ones.

PgBouncer's **pool mode** decides when a server connection is handed back:

| Mode | Server connection returned after | Compatibility |
|---|---|---|
| `session` | client disconnects | everything works; little multiplexing |
| `transaction` | each **transaction** ends | the usual choice — but session state breaks |
| `statement` | each statement | no multi-statement transactions; rarely used |

In **transaction mode**, consecutive transactions from the *same* client may run on *different*
server connections, so anything that lives in the *session* is unreliable:

- `SET app.tenant_id = '1'` (session-level) leaks to whoever gets that connection next → use
  **`SET LOCAL`** / `set_config(…, true)` inside the transaction.
- `LISTEN`/`NOTIFY` listeners, session advisory locks (`pg_advisory_lock`), temp tables, `WITH HOLD`
  cursors don't work. Use a direct (unpooled) connection for listeners and for session advisory
  locks (the singleton-job trade-off is in **Job Queues in PostgreSQL**), or
  `pg_advisory_xact_lock` when the work fits in one short transaction.
- Prepared statements: supported since PgBouncer 1.21 with `max_prepared_statements` set; on older
  versions disable them in the driver.

:::quiz id=db-16-q3 xp=15

connection, then runs queries that rely on RLS. What happens?
- [ ] It works — PgBouncer replays `SET` commands for each transaction
- [x] Later transactions may run on a server connection where the setting is missing or belongs to another tenant — use `SET LOCAL`/`set_config(…, true)` in every transaction
- [ ] PostgreSQL rejects `SET` when connected through a pooler

> A session-level `SET` sticks to the *server* connection, which transaction mode shares between
> clients. With RLS failing closed (`current_setting(…, true)` → NULL) you'd see empty results — or,
> worse, another tenant's id. Transaction-local settings are scoped exactly to the work they belong to.
:::

## VACUUM, autovacuum and bloat

Postgres uses **MVCC**: an `UPDATE` doesn't overwrite a row; it writes a new row version and marks
the old one dead (once no transaction can still see it). `DELETE` just marks. That's what lets
readers never block writers — and it means dead row versions pile up. **VACUUM** reclaims them
for reuse, updates the visibility map (which makes index-only scans possible) and **freezes** old
rows.

**Autovacuum** runs VACUUM and ANALYZE automatically when a table has changed enough (by default
50 rows + 20% of the table for vacuum; PG 18 adds `autovacuum_vacuum_max_threshold` to cap that
on huge tables). Leave it on. Tune it per table for big, hot ones:

```sql
ALTER TABLE render_jobs SET (autovacuum_vacuum_scale_factor = 0.01,   -- vacuum after 1% changes
                             autovacuum_analyze_scale_factor = 0.02);
```

What goes wrong in production:

- **Bloat**: when dead tuples are created faster than vacuum reclaims them, tables and indexes grow;
  scans read pages full of garbage. Queue tables with constant UPDATE/DELETE (the Job Queues lesson) are the
  classic victims. `VACUUM` makes space reusable but rarely shrinks files; `VACUUM FULL` rewrites the
  table under **ACCESS EXCLUSIVE** (an outage) — use `pg_repack` or `REINDEX CONCURRENTLY` instead.
- **Long-running transactions** — including an `idle in transaction` connection a buggy app left open —
  hold back the "oldest visible" horizon. VACUUM can't remove anything newer than that, for *any*
  table. Set `idle_in_transaction_session_timeout` and watch `pg_stat_activity`.
- **Transaction ID wraparound**: transaction ids are 32-bit. Rows must be *frozen* before ~2 billion
  transactions pass, or Postgres eventually stops accepting writes to protect your data.
  Autovacuum handles it — unless it's blocked by long transactions or turned off.

Queries worth bookmarking (run these on a real server; the in-browser database doesn't collect
these statistics):

```sql
-- tables with the most dead tuples and when they were last vacuumed
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

-- the oldest open transactions (the vacuum blockers)
SELECT pid, usename, state, now() - xact_start AS xact_age, left(query, 60)
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start LIMIT 10;

-- how close each database is to wraparound (alarm well before 2 billion)
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
```

## Replicas, failover and CDC

Sooner or later the studio database stops being one server. The primary gets **streaming
replicas** for failover and read scaling, and other systems (search, analytics, a data
warehouse) want to hear about every change. Each step changes what your application can
assume.

### Streaming replicas and replication lag

A **physical streaming replica** receives the primary's WAL over a replication connection and
replays it, so it's a byte-for-byte copy that accepts only reads (`hot_standby`). By default
replication is **asynchronous**: the primary commits, answers the client, and ships the WAL
afterwards. A replica is therefore always slightly behind, usually milliseconds and sometimes
seconds or minutes (a big batch update, a slow disk, a replica busy with a long report).

```sql
-- on the primary: how far behind is each replica?
SELECT application_name, state, sync_state, write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- on a replica: when was the last replayed transaction committed?
SELECT now() - pg_last_xact_replay_timestamp() AS replica_delay;
```

Lag causes the classic **read-your-writes bug**. A user renames a project (write to the
primary), the page reloads, the read goes to a replica that hasn't replayed the change yet, and
the old title comes back. The user renames it again. Common fixes, from simplest:

- **Read your own recent writes from the primary.** After a write, pin that user's reads to the
  primary for a few seconds (a cookie or a flag in the session).
- **Wait for the replica to catch up.** The app remembers the commit's position,
  `pg_current_wal_lsn()` on the primary, and the replica read waits until
  `pg_last_wal_replay_lsn()` has passed it.
- **Synchronous replication** (`synchronous_standby_names`, `synchronous_commit = remote_apply`)
  makes the primary wait until a replica has *applied* the commit. Reads are then consistent,
  but every commit pays a network round trip, and the primary stalls if that replica goes away.
  Most teams keep this for one standby that guards against data loss, not for read scaling.

Send only reads that tolerate staleness to replicas: reports, search pages, exports. Anything
inside a read-modify-write flow belongs on the primary.

### What failover means for the app

When the primary dies, an orchestrator (CloudNativePG, Patroni, or your managed service)
**promotes** a replica and repoints the service name or DNS to it. From the application's point
of view:

- every open connection to the old primary breaks, and **in-flight transactions are rolled
  back**. The app sees errors such as `57P01` (admin shutdown) or a dropped socket, and must
  **retry the whole transaction**, not just the last statement. This is the same retry loop you
  write for serialization failures (`40001`, see **Postgres From Your Code**), which only works
  if the transaction is safe to run twice (idempotency keys, upserts).
- with asynchronous replication, a transaction committed in the last instant before the crash may
  **not** have reached the new primary. That is your RPO for failover. Synchronous replication
  to at least one standby makes it zero.
- the connection string must point at something that follows the primary: a Kubernetes service
  such as CloudNativePG's `studio-db-rw`, a managed endpoint, or a multi-host string such as
  `Host=db1,db2;Target Session Attributes=primary` (Npgsql) that tries each host until it finds
  the writable one.
- connection pools hold dead connections after a failover. Use short connection lifetimes or the
  driver's pool-clearing on error, and expect a burst of reconnects.

### Logical replication and change data capture

Physical replication copies the **whole cluster** at the byte level, same major version only.
**Logical replication** decodes the WAL into row changes (`INSERT` / `UPDATE` / `DELETE` per
table) and sends them to a subscriber that can run a different major version, with a different
set of tables and indexes:

```sql
-- on the source
CREATE PUBLICATION studio_pub FOR TABLE projects, clips;
-- on the target (another Postgres)
CREATE SUBSCRIPTION studio_sub
  CONNECTION 'host=old-db dbname=studio user=replicator'
  PUBLICATION studio_pub;
```

It's used for major-version upgrades with near-zero downtime (see the next section), for moving
between providers, and for feeding a reporting database.

**Change data capture (CDC)** uses the same machinery to stream changes *out* of Postgres to
other systems. **Debezium** (usually on Kafka Connect) creates a **logical replication slot**
with the built-in `pgoutput` plugin and publishes every committed row change as an event: the
search index updates, the warehouse loads, caches are invalidated. Nobody has to remember to
call them from application code.

:::warn title="A replication slot is a promise to keep WAL"
A slot makes the primary keep every WAL segment its consumer hasn't confirmed. If the Debezium
connector is down for a weekend, the primary's disk fills up with WAL, and a full disk takes
the primary down. Alert on `pg_replication_slots` (`active`, and the WAL retained since
`confirmed_flush_lsn`), set `max_slot_wal_keep_size` as a safety valve, and drop slots nobody
uses. Slots also have to survive a failover: PostgreSQL 17+ can sync logical slots to standbys
(`failover = true`), and CloudNativePG and managed services expose that as a setting.
:::

### The transactional outbox, step by step

CDC on business tables has a catch: the events are shaped like your **schema**, not like your
**domain**. Rename a column and every consumer breaks. And "project published" is a business
event that doesn't map one-to-one to a row change. The **transactional outbox** (introduced in
the **Job Queues in PostgreSQL** lesson) solves both problems:

1. In the **same transaction** as the business change, insert an event row into an `outbox`
   table: a stable topic, a key, and a payload you design as a public contract.
2. A **relay** reads new outbox rows and publishes them to the broker (Kafka, RabbitMQ, a
   webhook).
3. Consumers receive **at-least-once** delivery and deduplicate by event id.

```sql
CREATE TABLE outbox (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  topic        text        NOT NULL,          -- 'project.published'
  key          text        NOT NULL,          -- partition key for the broker, e.g. the project id
  payload      jsonb       NOT NULL,          -- the public contract, versioned
  created_at   timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz                    -- set by the relay
);
CREATE INDEX outbox_unpublished_idx ON outbox (id) WHERE published_at IS NULL;
```

Because the event and the change commit together, you can never have one without the other.
Either the project is published *and* the event exists, or neither happened. Compare that with
"commit, then call Kafka": if the process dies between the two, the event is lost, and if Kafka
is down, the request fails after the data has already changed.

There are two ways to run the relay:

- **Polling:** a worker runs a `SKIP LOCKED` claim on unpublished rows (the Job Queues pattern),
  publishes the batch, then sets `published_at`. If it crashes after publishing but before the
  update, the batch is sent again. That's the at-least-once part.
- **CDC on the outbox table:** Debezium tails only `outbox` through a slot, and its *outbox
  event router* turns each insert into a message on the topic named in the row. There's no
  polling, and the events arrive in commit order.

Either way, delete or archive published rows on a schedule, as you would with finished jobs.

:::sql id=db-16-sql8 db=studio xp=60
title: Publish a project, with its event
Publishing a project must also emit a `project.published` event for the search indexer. Using
the `outbox` table from the setup, publish **project 2** at *now* = `'2025-07-10 17:00+00'` so
that the change and the event commit **together**:

- set `published = true`, increment `version` and set `updated_at` = now, but only if the
  project isn't published yet,
- insert one outbox row: `topic = 'project.published'`, `key` = the project id as text,
  `payload` = `{"project_id": …, "version": <the new version>, "owner_id": …}`, `created_at` =
  now. Leave `published_at` NULL, because that's the relay's job.

If the project was already published, nothing may be inserted.

The grader checks project 2's `published` and `version` and every outbox row.

hint: A data-modifying CTE: `WITH pub AS (UPDATE projects SET … WHERE id = 2 AND NOT published RETURNING id, version, owner_id) INSERT INTO outbox … SELECT … FROM pub;`
hint: `RETURNING` gives you the **new** `version`, after the increment.
hint: `jsonb_build_object('project_id', id, 'version', version, 'owner_id', owner_id)`

```sql setup
CREATE TABLE outbox (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  topic        text        NOT NULL,
  key          text        NOT NULL,
  payload      jsonb       NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz
);
```


```sql solution

  SET published = true, version = version + 1, updated_at = '2025-07-10 17:00+00'
  WHERE id = 2 AND NOT published
  RETURNING id, version, owner_id

SELECT 'project.published', id::text,
       jsonb_build_object('project_id', id, 'version', version, 'owner_id', owner_id),

```

## On call: diagnosing a slow or locked database

Sooner or later you get paged: *"the API is timing out"*. The database is the first suspect, and
you want answers in minutes. A good order of work:

1. **Is it the database?** Look at the connection count, CPU and I/O on the managed-service
   dashboard, and at `pg_stat_activity`.
2. **Is something blocked?** Find who is waiting and who holds the lock.
3. **Is something slow?** Find the expensive statements and their plans.
4. **Stop the bleeding**, then fix the cause in code or schema.

### What is running right now

```sql
SELECT pid, usename, application_name, state,
       now() - xact_start  AS xact_age,
       now() - query_start AS query_age,
       wait_event_type, wait_event,
       left(query, 80) AS query
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND state <> 'idle'
ORDER BY xact_start NULLS LAST;
```

Read it like this. `state = 'active'` with `wait_event_type = 'Lock'` means the session is
**blocked**. `idle in transaction` with a large `xact_age` is a session holding locks and
blocking VACUUM while doing nothing, usually an app that forgot to commit (the **Transactions,
Isolation & Locking** lesson). Hundreds of `active` sessions all running the same query point
to a missing index or a plan that flipped. Set `application_name` in every connection string
(`Application Name=studio-api` in Npgsql) so this view tells you *which service* is guilty.

### Who blocks whom: `pg_blocking_pids` and the lock tree

`pg_blocking_pids(pid)` returns the array of sessions that block `pid`. Joined with
`pg_stat_activity`, it's the fastest way to find the culprit:

```sql
SELECT pid,
       pg_blocking_pids(pid) AS blocked_by,
       state, now() - xact_start AS xact_age, left(query, 60) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0
   OR pid IN (SELECT unnest(pg_blocking_pids(pid)) FROM pg_stat_activity);
```

Blocking forms a **tree**. The `ALTER TABLE` from the lock-queue timeline above waits for an old
report, and a hundred API queries wait for the `ALTER`. Killing one of the hundred leaves helps
nothing. You want the **root**: the session that blocks others but isn't blocked itself. Then
decide:

```sql
SELECT pg_cancel_backend(4711);     -- cancel its current query (gentle; the session stays)
SELECT pg_terminate_backend(4711);  -- close the whole connection, rolling back its transaction
```

`pg_cancel_backend` doesn't help an `idle in transaction` session, because it isn't running a
query. Only terminating it ends the transaction. Write down what you killed and why: the root
blocker is the bug to fix after the incident.

:::sql id=db-16-sql9 db=empty ordered=true xp=60
title: Find the root blockers
During an incident you saved a snapshot of `pg_stat_activity` with `pg_blocking_pids(pid)` into
the table `activity` (see the setup). `blocked_by` is the array of pids that block each session;
an empty array means "not waiting".

Return the **root blockers**: sessions that are not blocked themselves but block at least one
other session. For each one, return `pid`, `state` and `waiting`, the number of **distinct**
sessions waiting on it **directly or indirectly**. Order by `waiting` descending, then `pid`.

hint: Start a `WITH RECURSIVE` from the roots: `cardinality(blocked_by) = 0` and some other row has `pid = ANY(blocked_by)`.
hint: Recursive step: `JOIN activity w ON t.pid = ANY(w.blocked_by)`, carrying the root along.
hint: Session 105 waits on both 101 and 102. Count it once: `UNION` (not `UNION ALL`) or `count(DISTINCT …)`.

```sql setup
CREATE TABLE activity (
  pid        int PRIMARY KEY,
  state      text     NOT NULL,
  blocked_by int[]    NOT NULL,
  xact_age   interval,
  query      text     NOT NULL
);
INSERT INTO activity VALUES
  (101, 'idle in transaction', '{}',        '00:42:10', 'UPDATE projects SET title = $1 WHERE id = $2'),
  (102, 'active',              '{101}',     '00:03:05', 'ALTER TABLE projects ADD COLUMN slug text'),
  (103, 'active',              '{102}',     '00:02:59', 'SELECT * FROM projects WHERE id = $1'),
  (104, 'active',              '{102}',     '00:02:40', 'SELECT * FROM projects WHERE owner_id = $1'),
  (105, 'active',              '{102,101}', '00:02:10', 'UPDATE projects SET version = version + 1 WHERE id = $1'),
  (201, 'active',              '{}',        '00:00:12', 'UPDATE render_jobs SET status = ''running'' WHERE id = 7'),
  (202, 'active',              '{201}',     '00:00:08', 'UPDATE render_jobs SET status = ''failed'' WHERE id = 7'),
  (301, 'active',              '{}',        '00:00:01', 'SELECT count(*) FROM clips');
```

```sql starter
SELECT pid, state, 0 AS waiting
FROM activity
WHERE cardinality(blocked_by) = 0
ORDER BY pid;
```

```sql solution
WITH RECURSIVE tree AS (
  SELECT a.pid AS root, a.pid
  FROM activity a
  WHERE cardinality(a.blocked_by) = 0
    AND EXISTS (SELECT 1 FROM activity w WHERE a.pid = ANY (w.blocked_by))
  UNION
  SELECT t.root, w.pid
  FROM tree t
  JOIN activity w ON t.pid = ANY (w.blocked_by)
)
SELECT r.pid, r.state, count(*) - 1 AS waiting
FROM tree t
JOIN activity r ON r.pid = t.root
GROUP BY r.pid, r.state
ORDER BY waiting DESC, r.pid;
```
:::

### Slow queries: the slow log, `pg_stat_statements` and `auto_explain`

Locks explain *stuck*. For *slow*, you need history, and three tools give it to you. Turn them
on **before** the incident:

- **`pg_stat_statements`**: the top statements by total time, the starting point from
  **Performance Tuning**. Compare it with yesterday's numbers to see what changed.
- **The slow-query log**: `log_min_duration_statement = '500ms'` logs every statement slower
  than that, with its duration and parameters. Add `log_lock_waits = on` (logs waits longer
  than `deadlock_timeout`) and `log_temp_files = 0` (shows sorts and hashes spilling to disk).
- **`auto_explain`**: logs the **plan** of slow statements as they run in production, which is
  the only way to see the plan the app really got, with its real parameters:

```text
# postgresql.conf (or the managed service's parameter settings)
shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = '1s'
auto_explain.log_analyze = on      # real row counts and timings (adds overhead; sample if busy)
auto_explain.log_buffers = on
auto_explain.sample_rate = 0.1     # explain 10% of qualifying statements
```

A plan that "suddenly" got slow is usually a **plan flip**: statistics changed after a bulk load,
a value became very common, or a generic plan for a prepared statement got cached. Compare the
logged plan with `EXPLAIN (ANALYZE, BUFFERS)` and look at estimate vs actual rows (**Performance
Tuning**, "Statistics").

### Managed Postgres: what changes, what doesn't

Most teams run Postgres as a service: **Amazon RDS / Aurora**, **Azure Database for PostgreSQL
Flexible Server**, **Google Cloud SQL / AlloyDB**, or serverless offerings such as **Neon** and
**Supabase**. The SQL in this region works the same. The operations differ:

- **No superuser and no shell.** You get an admin role with most privileges (`rds_superuser`,
  `azure_pg_admin`), extensions from an allow-list, and no `postgresql.conf` to edit.
- **Settings live in parameter groups or server parameters.** `shared_preload_libraries`,
  `log_min_duration_statement` and the `auto_explain.*` settings are set in the console or with
  infrastructure-as-code, and some need a **restart**, which is a maintenance window.
- **Backups, PITR, replicas and failover are checkboxes.** You still own restore drills, and you
  still own retries in the app.
- **Monitoring is built in** (Performance Insights on RDS, Query Store on Azure, Query Insights
  on Cloud SQL), and it's built on the same `pg_stat_*` views you've seen here.
- **Connection limits scale with the instance size**, and serverless offerings scale to zero and
  wake up on the first connection, so expect a cold-start delay. Most of them include a pooler
  that runs in transaction mode, with the session-state rules from the pooling section.

### Major-version upgrades

Minor releases (18.0 to 18.1) are drop-in binary updates: apply them promptly, they're
security and bug fixes. **Major** versions (17 to 18) change the on-disk format, so the data
has to be converted. There are three ways, from simplest to least downtime:

| Approach | Downtime | Notes |
|---|---|---|
| `pg_dump` + restore into the new version | hours for big DBs | simplest, also changes provider or hardware |
| **`pg_upgrade`** (`--link` or `--clone`) | minutes | rewrites the catalogs in place. This is what in-place upgrades on RDS and Azure run. PG 18 keeps most planner statistics; still run `vacuumdb --all --analyze-in-stages --missing-stats-only` afterwards so extended statistics are rebuilt |
| **logical replication** to a new cluster, then switch | seconds | blue/green: build an 18 cluster, subscribe it to the 17 one, let it catch up, stop writes, switch the connection string. RDS *Blue/Green Deployments* automate this. Sequences and DDL are not replicated, so sync them yourself |

Whatever the method: upgrade a **staging copy** first, run the test suite against it (Testcontainers
on the new image), check that every extension has a version for the new major, read the release
notes' "incompatibilities" section, and have a rollback plan. Rolling back after a `pg_upgrade
--link` means restoring a backup.

:::quiz id=db-16-q8 xp=15
Page at 03:10: API requests to `/projects` time out. `pg_stat_activity` shows 180 sessions in
`active` waiting on `Lock`, one `ALTER TABLE projects …` from the deploy pipeline also waiting
on `Lock`, and one session `idle in transaction` for 47 minutes whose last query was an `UPDATE
projects …` from a support script. What do you do first?

- [ ] `pg_cancel_backend` the 180 waiting API sessions so the pool recovers
- [ ] `pg_cancel_backend` the idle-in-transaction session
- [x] `pg_terminate_backend` the idle-in-transaction session (the root blocker), then make sure the migration has a `lock_timeout` before it retries
- [ ] Restart the database server
> The idle session holds a row lock on `projects` (and its `ROW EXCLUSIVE` table lock). The
> `ALTER TABLE` queues for `ACCESS EXCLUSIVE` behind it, and every API query queues behind the

> back. `pg_cancel_backend` cancels a *running query*, and an idle-in-transaction session has
> none, so only `pg_terminate_backend` ends its transaction. A restart works too, but it drops
> every connection and loses the evidence. Afterwards: `idle_in_transaction_session_timeout` for
> scripts, and `lock_timeout` in the migration tool.

:::cards id=db-16-cards1 xp=20 title="Production Postgres"
Q: Expand / contract in one sentence?
A: Add the new schema alongside the old, migrate data and code over several deploys, and only then remove the old.
Q: Why set `lock_timeout` in migrations?
A: A waiting ACCESS EXCLUSIVE request blocks every query queued behind it; fail fast and retry instead of stalling the site.
Q: Which `ADD COLUMN … DEFAULT` rewrites the table (PG 11+)?
A: Only a volatile default (`gen_random_uuid()`, `clock_timestamp()`). Constants and stable functions like `now()` are stored once in the catalog — metadata-only.
Q: How to add a CHECK/FK to a big table safely?
A: `ADD CONSTRAINT … NOT VALID` (instant, enforces new writes), then `VALIDATE CONSTRAINT` (scans without blocking writes).
Q: How to SET NOT NULL without a long lock?
A: Validated `CHECK (col IS NOT NULL)` first (or PG 18 `NOT NULL … NOT VALID` + VALIDATE), then SET NOT NULL skips the scan.
Q: Why backfill in batches?
A: Small committed transactions avoid long row locks, WAL spikes, replica lag and huge rollbacks; `WHERE new_col IS NULL` makes it resumable.
Q: What does `ALTER DEFAULT PRIVILEGES` solve?
A: Grants for tables created in the future — `GRANT … ON ALL TABLES` only covers existing ones.
Q: Who bypasses row-level security?
A: Superusers, roles with BYPASSRLS, and the table owner (unless FORCE ROW LEVEL SECURITY). Views also read as their owner unless created with `security_invoker = true`.
Q: Why `nullif(current_setting('app.tenant_id', true), '')`?
A: After a setting was used on a connection, "unset" means `''`, and `''::int` errors. nullif turns it into NULL → no rows (fail closed).
Q: USING vs WITH CHECK in a policy?
A: USING filters rows you can read/update/delete; WITH CHECK validates rows you write.
Q: pg_dump vs WAL archiving?
A: pg_dump = logical snapshot at one moment; base backup + WAL archive = restore to any point in time (PITR).
Q: SET vs SET LOCAL behind PgBouncer transaction mode?
A: Session `SET` leaks across clients sharing a server connection; `SET LOCAL` lasts only for the current transaction.
Q: What blocks VACUUM from cleaning dead rows?
A: Long-running or idle-in-transaction sessions (and old replication slots / prepared transactions) holding back the xmin horizon.
Q: What is the read-your-writes bug?
A: A write goes to the primary, the next read goes to an asynchronous replica that hasn't replayed it yet, and the user sees old data. Pin recent writers to the primary or wait for the LSN.
Q: What does a failover mean for the app?
A: Connections break and in-flight transactions roll back; retry whole transactions, point at an endpoint that follows the primary, and accept the async RPO.
Q: Why use a transactional outbox instead of CDC on business tables?
A: The event commits with the change, and its payload is a designed contract, not your table layout. A relay (polling with SKIP LOCKED, or Debezium on the outbox) publishes it at least once.
Q: How do you find the root of a lock pile-up?
A: `pg_blocking_pids(pid)` with `pg_stat_activity`; follow the tree to the session that blocks others but isn't blocked. Cancel its query, or terminate it if it's idle in transaction.
Q: Which tools show slow queries after the fact?
A: `pg_stat_statements` (totals), `log_min_duration_statement` (the slow log) and `auto_explain` (the real production plans).
Q: Three ways to do a major-version upgrade?
A: dump/restore (hours), `pg_upgrade` (minutes, what in-place managed upgrades use), logical replication to a new cluster and switch (seconds, blue/green).
:::

## Recap

- Schema changes are **migrations**: versioned, reviewed, tested in CI, run once as a separate deploy
  step; never edit an applied migration.
- Zero downtime = **expand → migrate → contract**, and every migration must work with the app version
  still running.
- Watch the **locks**: `lock_timeout`, `NOT VALID` + `VALIDATE`, `CREATE INDEX CONCURRENTLY`, batched
  backfills, dual-write triggers for renames.
- **Least privilege**: owner/migrator/app/reporting roles, append-only tables via REVOKE, default privileges.
- **RLS** makes tenant isolation a database guarantee — connect as a non-owner, set the tenant with
  `set_config(…, true)` per transaction, use `WITH CHECK`.
- **Backups**: pg_dump for portability, base backup + WAL archiving for PITR (CloudNativePG + Barman
  Cloud), and restore drills to know your real RTO.
- **Pool** connections (client pools + PgBouncer); transaction mode means no session state.
- **VACUUM** is MVCC's garbage collector: keep autovacuum on, tune hot tables, kill long transactions,
  watch wraparound age.
- **Replicas lag**: route only staleness-tolerant reads to them, retry whole transactions after a
  failover, and watch replication slots. Publish domain events through a **transactional outbox**.
- **On call**: `pg_stat_activity`, then `pg_blocking_pids` to the root blocker, then the slow log,
  `pg_stat_statements` and `auto_explain`. On managed Postgres the knobs live in parameter
  settings, and major upgrades go through `pg_upgrade` or a logical-replication blue/green switch.
